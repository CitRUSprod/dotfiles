---
description: Создаёт коммит и пушит его (build) или предлагает сообщение (plan), определяя язык по последним коммитам. Файлы нужно предварительно проиндексировать через git add.
---

Сначала проверь, что в индексе есть изменения (`git diff --cached --stat`). Если индекс пуст — сообщи, что нечего коммитить, и прекрати выполнение. Никогда не выполняй `git add` самостоятельно — используй только то, что уже находится в индексе (staged).

Проанализируй застейдженные изменения (`git status`, `git diff --cached`) и определи тип изменений в conventional commit формате.

Важно: никогда не коммить напрямую в master/main. Если текущая ветка — master или main, придумай краткое название новой ветки в kebab-case на основе изменений (например, `feat/add-user-auth`, `fix/login-bug`). Команда всегда должна создавать новую ветку в этом случае.

Чтобы определить язык коммитов проекта, посмотри несколько последних сообщений:

```
git log --oneline -5 --format="%s"
```

Если в истории ещё нет коммитов — язык по ним определить нельзя, поэтому уточни у пользователя, на каком языке писать сообщение коммита.

Посмотри застейдженные изменения:

```
git status
git diff --cached
```

Сгенерируй сообщение коммита по формату и правилам ниже. Сообщение должно быть кратким, использовать conventional commit format: `тип(scope): описание`. Опционально можно указать scope — область изменений (например, `feat(api):`, `fix(auth):`).

Допустимые типы:
- `feat` — Новая функциональность
- `fix` — Исправление ошибки
- `docs` — Изменения в документации
- `style` — Изменения, не влияющие на смысл кода (форматирование, отступы и т.д.)
- `refactor` — Изменение кода без исправления ошибок и добавления функциональности
- `perf` — Изменения, улучшающие производительность
- `test` — Добавление или исправление тестов
- `build` — Изменения в системе сборки или внешних зависимостях
- `ci` — Изменения в конфигурации CI
- `chore` — Прочие изменения, не затрагивающие src или тесты
- `revert` — Откат предыдущего коммита

Описание должно быть на языке, определённом по последним коммитам или уточнённом у пользователя, и начинаться с заглавной буквы.

Примеры:
- `feat(api): Добавить эндпоинт для получения пользователей`
- `fix: Исправить ошибку валидации email`

Важно: команда не добавляет файлы в коммит автоматически. Перед вызовом /commit-and-push проиндексируйте нужные изменения через `git add <файлы>` или `git add -p`.

Никогда не используй флаг `--no-verify` с git commit.

Если сессия только для чтения (plan mode): выведи предложенное название ветки (если нужна новая) и сообщение коммита без внесения изменений и прекрати выполнение.

Если сессия позволяет выполнять команды (build mode):
- Если текущая ветка — master/main, создай новую: `git checkout -b <название-ветки>`.
- Выполни коммит:

```
git commit -m "<сообщение>"
```

- Перед пушем определи, есть ли у текущей ветки upstream (`git rev-parse --abbrev-ref --symbolic-full-name @{upstream}`):
    - Если upstream есть — выполни пуш на его remote:

        ```
        git push -u <remote> HEAD
        ```

        где `<remote>` — первая часть upstream (например, для `origin/feat/foo` это `origin`). Извлекается командой `git rev-parse --abbrev-ref --symbolic-full-name @{upstream} | cut -d/ -f1`.
    - Если upstream отсутствует (команда завершилась ошибкой) — проверь `git remote`:
        - Если remote-ов нет — сообщи, что пушить некуда, и попроси добавить репозиторий командой `git remote add <url>`.
        - Если remote один — выполни `git push -u <remote> HEAD`.
        - Если их несколько — уточни у пользователя, на какой remote пушить.
